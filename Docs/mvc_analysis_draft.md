The Controller class for this sprint, CustomerController, is where every Create, Read, Update and Delete action on a customer record actually happens. CreateCustomer takes the raw details a form would collect, customer number, name, contact details, and a staff flag, and either builds a Customer or a StaffCustomer from them. Before it does that it checks whether the customer number is already taken and, if so, returns null instead of adding a duplicate, leaving the calling form to check that return value and show a message, rather than the Controller throwing an exception for what is really just an expected outcome of someone typing in an existing ID. Read is split across three methods depending on what the caller needs: GetAllCustomers for populating a list, GetCustomerByNumber when a specific record has to be found, and GetCustomerByIndex so a view that displays customers in a ListBox or ComboBox can map a selected row back to the object it represents without ever holding the list itself. Update and Delete, UpdateCustomerDetails and DeleteCustomer, both look the customer up first and return a bool so the form always knows whether the action actually happened.

The UI flexibility comes from the fact that none of this logic cares what is calling it. MainForm, CustomerForm and ManageCustomersForm all hold a reference to the same CustomerController, but not one of them stores a List<Customer> of their own. GetAllCustomers always hands back a fresh copy, so even if a form tried to add or remove something from what it gets back, the Controller's own records would be unaffected. That separation means the three Windows Forms could be replaced with a console menu, a web page, or a different GUI framework entirely, and CustomerController, Customer and the Account hierarchy underneath it would not need to change at all. The business rules live in one place, and the interface is just whatever happens to be asking it questions at the time.
